# Phase 0 host probe results

## Scope and safety

The probe ran against the installed Copilot CLI `1.0.90-0` on Windows. It did not
connect to OpenViking or read, create, modify, or delete any Viking server data.
Probe files are installed under the Copilot user extension and hook directories;
NDJSON results are ignored by Git under `.probe-results/`.

Recorded data is metadata-only: event names, field names, timestamps, sequence
numbers, process IDs, booleans/numbers needed for the contract, string lengths,
and truncated SHA-256 fingerprints of event/parent/session IDs. Conversation
strings, tool arguments, tool results, raw IDs, and hook input values are not
persisted.

### Remote idempotency probe (2026-10-02)

A unique `ov-copilot-it-*` session was created, one synthetic message with a
fixed `source_message_ids` value was posted twice, and the session was then
deleted. `message_count` was 1 after the first write and 2 after the second, so
the server accepted the duplicate: it does **not** deduplicate on
`source_message_ids`. Therefore the at-least-once window (remote accepted, local
acknowledgement not yet persisted) can produce a duplicate remote message. Local
replay deduplication is unaffected; this is a server-side gap to close before
claiming exactly-once delivery.

### Live-session backlog during a transient transport failure (2026-10-02)

While this session was running with the integration active, its partition
accumulated 212 queued records (about 141 KB) with a stable acknowledged
cursor. Diagnostics showed six `session-unavailable` events with an empty
status and `category: retryable`, plus exponential `capture-retry-scheduled`
delays of roughly 1 s, 2 s, 3.4 s, 7.7 s, 15 s, and 37 s, and one
`session-end-commit-skipped` with `reason: capture-pending`. A direct
`/api/v1/system/status` call from a separate client returned 200 in 233 ms, so
the server was healthy: the stall was transient transport failure, and capture
correctly kept the records durable instead of dropping them.

Driving the same runtime with bounded flush rounds drained the backlog
(234 → 0 records; acknowledged 667 → 909 = observed; no dead letters) and the
remote session reached 103 messages. Two operational notes follow:

- The current retry policy can leave a visible backlog for tens of seconds
  after a transient failure, because capture has no socket timeout of its own
  and each attempt is only scheduled by a later event, stop, or end hook.
- `/clear` or session end can therefore skip a commit for the session even
  though its data is safe in the journal; the next flush completes it.

Neither loses data. After this observation the default retry cap was reduced
from 60 s to 15 s so a stalled flush cannot stay unchallenged for a minute; a
new event still resets the schedule through `flushPending`. A per-write socket
timeout remains the more complete fix and is not yet implemented.

### Extension approval gates MCP tool availability (2026-10-09)

On CLI `1.0.94-3`, a user reported a fresh session where the OpenViking MCP
tools were not registered and the agent fell back to the `ov` CLI. Diagnosis:

- The extension process launched and reported `=== ready ===` in every reviewed
  session, and always ended `=== exit code=1 disposition=stopped-normally ===`,
  which is the host's normal stop signal rather than a crash.
- The installed proxy is healthy on its own: a direct stdio handshake returns
  server `openviking-mcp`, version `v0.1.0`, with 14 tools including `health`.
- In sessions where the host listed the proxy (`server_info: … openviking-mcp`),
  the OpenViking tools were available; a live call to `openviking-health`
  succeeded. In sessions where the host never listed it, no `openviking` MCP
  registration appeared in the main log at all.

Conclusion: the OpenViking MCP server is registered dynamically by the
extension at session join, so it exists only where the extension actually
loaded. Copilot asks before loading a user-level extension that registers hooks,
and in a fresh directory or a `-p` run the prompt may be auto-denied
(`ExtensionDeniedError`). That state looks exactly like "OpenViking MCP is not
installed" and the `ov` CLI fallback is a correct observation, not a bug.
Approving the extension (once per session, or "always allow" per directory)
restores both recall/capture and the MCP tools. This is host approval behavior,
not an integration defect; it is documented in the README. Persisting the
approval across directories without a per-directory prompt was not located in
the CLI, so this remains a small ergonomic gap rather than a correctness issue.

## MCP tools connected but not projected (2026-10-09/10)

A testing agent reported a session on CLI `1.0.94-3` where the OpenViking MCP
tools were absent from the model's list while everything else looked healthy:
the extension was `running` (user scope), permissions were granted, the CLI log
showed the `openviking-mcp` handshake, and recall/capture worked. After an App
resume the 14 tools appeared with no further approval. That is a third state,
distinct from "extension denied":

- **denied** — extension never loads; no recall/capture and no MCP tools;
- **connected but not projected** — extension runs, server handshakes, but the
  session's tool catalog does not include the server's tools;
- **projected** — the tools are listed for the model.

Root cause: the host projects the MCP tool catalog asynchronously, so a
successful handshake proves only that the server answered — not that the model
can see its tools. `mcp-servers-loaded` and the per-server status are ordinary
session events, but there is no dedicated "catalog updated" event (only the
generic `tools-updated`).

Fix in this repo: on `onSessionStart`, after the runtime is ready, the extension
now verifies the projection through `session.rpc.tools.getCurrentMetadata()`
(the authoritative "initialized tool set" snapshot, matched on
`mcpServerName === "openviking"`). A `null` set means tools were never
initialized — normal for an idle session — and is reported as
`mcp-tools-not-yet-initialized`, never as a fault. If the set exists but the
OpenViking tools are missing, the extension calls `session.rpc.mcp.reload()`
once and re-checks, logging `mcp-tools-missing-after-handshake` and
`mcp-tools-projection-recovered`. Running this inside `onSessionStart` matters:
the host finalizes the first catalog after hooks resolve, so a reload there
lands before the model's first tool list. Each state emits its own event so
"connected" and "tools available" can never be collapsed into one claim.

Verified on CLI `1.0.95-3` in a real terminal session:

```
mcp-projection-check-start {"serverName":"openviking"}
mcp-server-connected {"connectedClients":[…7 incl. openviking…],"hostReportsOpenViking":true,"status":"connected"}
mcp-tools-projected {"projected":14,"sample":["add_resource","add_skill","edit"],"available":true}
```

Failure found and fixed during this work: the first revision created the
verifier at module top level, before the top-level `await joinSession(...)`
resolved, so it captured `session` while still in its temporal dead zone and
the extension died at import with `ReferenceError: Cannot access 'session'
before initialization`. That crash silently disabled recall, capture, and MCP.
The verifier is now assigned only after `joinSession` resolves, and a regression
test (`test/extension-structure.test.mjs`) pins that ordering.

Limits: this verifies the projection for the current session and issues one
reload; it is not a general guarantee that the host re-project a late server on
every version, and the reload perturbs other MCP servers, which the host
recomputes.

### Capture write timeout correction (2026-10-23)

An earlier note claimed capture had no per-write timeout of its own. That was
wrong. Measured against a socket that accepts the connection and never replies:

| Operation | Requested budget | Actual abort |
|---|---|---|
| Session read | 15 s | 15 018 ms, `AbortError` |
| Capture write | 30 s | 30 005 ms, `AbortError` |

Both paths are bounded by an `AbortController`. The real defect was the size of
the default: the upstream derives a 30 s capture budget, so a single hung socket
consumed half a minute before the queue was even retried — which is what made the
observed backlog look like a stall. `src/copilot-memory-session.mjs` now clamps
each write to `MAX_CAPTURE_WRITE_TIMEOUT_MS` (10 s) while still honouring any
shorter configured value and the compaction deadline. Two tests cover the clamp
and the pass-through of a shorter value.

An isolated `COPILOT_HOME` cannot be used for this matrix: an unauthenticated
home returns 403 for the model catalog and disables third-party MCP by policy,
so extension behaviour cannot be observed there. The runtime matrix therefore
uses the signed-in normal profile with a scratch workspace.

## Bounded transcript catch-up at compaction (2026-10-22)

The earlier gate could only refuse. If the host had written an event to
`events.jsonl` just before the Hook ran and the extension had not yet journaled
it, the audit blocked the commit and the event was simply lost from that
archive — safe, but not complete. That is the "capture completeness at Hook
time" gap.

The fix splits the problem by evidence quality. A missing event that the
**transcript** already contains is proven to have happened before the Hook, so
it is journaled from that authority rather than guessed at:

1. flush the durable queue;
2. audit; if events are missing, take the missing list;
3. journal that tail through the same durable store (same ordering,
   deduplication, and digest ledger), bounded to 16 events;
4. flush again and re-audit;
5. commit only if the re-audit passes.

A gap larger than the bound is refused with `catch-up-too-large` and no commit.
That boundary is deliberate: a large gap means the session was captured by an
earlier process or resumed, which is historical replay — explicitly out of
scope because host event identity across reload/resume is unproven. Changed
payloads are also not caught up: the ledger keeps the original digest, so
staging the altered event is refused by the store.

Verified live on CLI `1.0.95-3` in a real terminal session (run-scoped
integration mode, synthetic content). The host recorded:

| Offset | Event |
|---|---|
| +0.004 s | `hook.start`, `hookType: preCompact` |
| +1.303 s | `hook.end`, `hookType: preCompact`, `success: true` |
| +14.551 s | `session.compaction_complete` |

The run-scoped session reported `commit_count: 1` and `pending_tokens: 0`, so
the catch-up path did not disturb a normal compaction. That run had no tail to
catch up; the tail path itself is covered by the synthetic tests below, which
exercise a real transcript file and a real durable store.

New tests: `test/transcript-catchup.test.mjs` (boundary at exactly 16, refusal
above it, idempotent second pass, normalization mismatch, store failure) and
`test/pre-compact-catchup.test.mjs` (end-to-end catch-up then commit, oversized
gap never commits, changed payload never commits). Full suite: 108 passing.

Remaining limit: this closes the case where the host wrote the event before the
Hook. An event the host had *not* yet written when the Hook ran still cannot be
seen by any reader, and no local mechanism can change that ordering.

## Important finding: MCP launcher

The first MCP attempt used the extension process's `process.execPath`. In the
Copilot-hosted extension, this path points to the Copilot executable, which tried
to parse the MCP script as a CLI command and exited before handshake. The
installer's Node process reported the actual Node executable; passing that
validated absolute path fixed stdio server startup and the MCP initialize/tools
flow.

Production must use an explicit runtime resolver and fail with a diagnostic if it
cannot find a compatible Node executable. Do not silently fall back to
`process.execPath`.

## Consequences for the design

1. Keep the SDK extension as primary runtime and continue registering OpenViking
   MCP per joined session.
2. Add an explicit Node executable discovery step to the installer and diagnostics.
3. Use `event.id` as the preferred event identity, but test its stability across
   reload and resume before persisting it as a hard cursor.
4. Treat configured subagent hooks as capability-conditional. SDK lifecycle events
   are available for the tested agent; do not claim universal first-prompt injection.
5. Two real `/compact` runs verified the disabled-memory path. An instrumented
   memory-enabled run captured `pre-compact-complete`, exit code 0, and no
   watchdog 8.414 seconds before `session.compaction_complete`; the remote
   `last_commit_at` timestamp lagged the host event. This verifies ordering for
   one invocation, not a general host deadline guarantee or completeness of
   events not yet durable in the shared journal.
